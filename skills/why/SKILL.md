# Why（なぜこうなっているか）

コードの形を決めた力を調べる。`how` が「何をするか」を答えるのに対し、`why` は「なぜその形になったか」を答える。

証拠は git 履歴、PR の本文とレビュー、コミットメッセージのチケット番号、リポジトリ内の文書（`docs/`、ADR、`README`）から集める。集めた証拠には必ず出典（コミット、PR 番号、ファイルと行）を付ける。

## Start

開始前に、フェーズごとに 1 項目の todolist を開く。

1. Frame
2. Anchor
3. Investigate
4. Read out

## Phase A: Frame（対象と問いを決める）

対象は、コードの一区画、パターン、機能、名前の付いた設計判断のどれか。問いは、動機、代替案との比較、前提になった制約、死んだコード、広い経緯のどれか。

対象が曖昧なら、文脈から最も妥当な読みを 1 文で宣言してから進む。

## Phase B: Anchor（コードの錨を張る）

調査を投げる前に、自分で次を集める。この錨をすべての調査に渡す。

- ファイルのパスと行の範囲、キーになるシンボル（関数・クラス・定数）
- `git blame -L <start>,<end> <file>` で、最後に触ったコミット
- `git log --follow --oneline -- <file>` で、改名をまたいだ履歴
- 変更のあったコミットの PR 番号（`git log -1 --format=%B <commit>` と、件名の `(#1234)`）
- PR の本文とレビュー。forge は `models.md` の `forge` 行に従う。GitHub なら `gh pr view <n> --json title,body,author,createdAt,mergedAt,comments,reviews`

## Phase C: Investigate（切り口ごとに並列で調べる）

証拠の種類ごとに切り口を分け、`subagent-ctl` で同時に調べる。使える切り口だけを使う。

| 切り口 | 見るもの |
|---|---|
| 履歴 | コミットの並び、変更の単位、戻された変更 |
| 議論 | PR の本文とレビュー、コミットメッセージの本文 |
| 課題 | チケット番号から辿れる背景と制約 |
| 文書 | `docs/`、ADR、`README`、コードのコメント |
| データ | 閾値や設定値の根拠（計測・実験の記録があれば） |

`spawn(<name>, readonly, --role code)` → `send(<id>, <錨と切り口>)` → `wait(<id>)` → `read(<id>, <lines>)` → `stop(<id>)`。モデルは `code` ロール。

見つからなかった切り口も記録する。「調べたが無かった」は結果であり、抜けではない。

## Phase D: Read out（引用付きで返す）

次の形で返す。当てはまらない項目は落とす。

- **決定**: 何が決まっているか。ファイルと行を示す
- **理由**: その決定を押した力（障害、制約、要望、期限）
- **代わりの案**: 検討されて捨てられた案と、捨てた理由
- **制約**: いまも残っている前提。これが崩れると決定も崩れる
- **出典**: コミット、PR 番号、文書の該当箇所
- **確信度**: 各主張に「実測」「記録あり」「推測」のラベルを付ける

## ルール

- 出典を示せない主張は、事実として書かない。推測なら推測と書く
- 決定の理由が見つからないときは、無いと書く。もっともらしい理由を創作しない
- コードは変えない。設計をやり直す必要があると分かったら、その旨を報告して別のタスクにする
