# Swarm（並列検証）

## Start

開始前に、フェーズごとに 1 項目の todolist を開く。

1. Frame
2. Fan out
3. Aggregate
4. Report

## Phase A: Frame

1. 完了述語と、swarm が返すべき artifact・レポートを宣言する。
2. 形を選ぶ。スライスに分割 / 同一 brief で N ワーカーを競わせる / 混合。競わせる場合は `first pass` / `rank all` / `best-of` を先に宣言する。スライスの重なりは 1 回確認する（同じ面を別の入口から叩くのは可。同じ検査のやり直しは不可）。
3. ワーカーのモデルは `swarm workers` ロール（`~/.config/omakase/models.md` に指定があればその値、無ければ inherit-parent）。
4. 各ワーカーに、書くときは自分の書き込み先を与える。コミットを検証・計測する場合、brief は正確な SHA を名指しする。計測 brief は方法（サンプル数・1 サンプルとは何か・順序）も名指す。ワーカーは結果に両方を記録する。
5. 報告先と期限を決める。報告は `<cwd>/.swarm/<name>.md` の 1 ファイル（端末の `read` は画面で切れる）。期限はワーカーごとに分単位で決める。

## Phase B: Fan out

N ワーカーを並列に起動する（`subagent-ctl` の `spawn` を N 回。モデルは `swarm workers` ロール）。隔離が必要な書き込みは `fleet_fork`（Pi のワークツリー）か、ワーカーごとの別 cwd で行う。読み取り専用の検証なら同一 cwd の別出力先でよい。

各 brief は自立していること。目標・範囲・正確なスライスまたはレース腕・検証方法・報告先・期限・報告内容を含める。

報告の型（brief にそのまま書く）:

- 1 行目は `RESULT: PASS (方法, ケース数)` / `RESULT: ISSUES (n 件)` / `RESULT: BLOCKED (理由)`。
- ISSUES は 1 件 3 行まで（再現コマンド / 期待 / 実際）。断定できないものは「未確認」と書く。
- 欠陥を証明できたワーカーは、最初の 1 件だけでなく証明できる全件を列挙する。
- 既存テストの緑は証拠に数えない。証拠は自分で実行したコマンドと出力。

ワーカーが落ちたら N-1 で進め、その旨を記す。

## Phase C: Aggregate

1. 報告ファイルを読む（端末の `read` ではなく）。brief が名指した SHA・方法・ケース数を記録しない結果は捨て、そのワーカーを 1 回だけ再起動する。2 回目も欠けたらギャップとして記録する。ギャップは合格に数えない。
2. ISSUES のうち 1 件以上を自分で再現する。再現しないものは「未確認」に分離し、修正の根拠にしない。
3. 停滞は期限で判定する。子ごとに `wait <id> --timeout <N>` で待ち、戻りの `reason` で分岐する。`status` はターン終了（報告ファイルを見る）、`timeout` は N 秒後もまだ作業中、`exit` / `error` / `blocked` は脱落。`timeout` が続いて期限を過ぎたら `interrupt` → `status` を読む → 同じ brief で 1 回だけ再起動し、2 回目も駄目なら BLOCKED として集計する。読み取り専用の仕事は push や PR の活動では判定できない。
4. カバレッジでは、必要な全スライスに結果が要る。レースでは、先に宣言した規則を適用する。生のワーカー出力を貼り付けない。

## Phase D: Report

1 つの統合レポートを返す。結果表、問題の 1 行要約、ギャップ・脱落、レース規則（使った場合）、親が再現した件数と未確認の件数。
