# How（どう動くか）

対象のサブシステムを読み、「どう動くか」を説明する。読むだけの調査で、コードは変えない。

出す説明の水準は、シニアエンジニアがそのサブシステムに配属されたときに作業できる心的モデルまで。注釈付きのソースコードのようにはしない。

## Start

開始前に、フェーズごとに 1 項目の todolist を開く。

1. Assess
2. Explore
3. Synthesize
4. Present

## Phase A: Assess（複雑度を決める）

対象の範囲が曖昧なら、自分の解釈を 1 文で宣言してから進む。違っていれば人は軌道を戻せる。

- **単純**: 1 モジュール、小さなユーティリティ、「関数 X はどう動くか」のような狭い問い。explorer は立てず、explainer 1 本が調べて説明する
- **複雑**: 複数ファイル・複数サービスにまたがるサブシステム、横断的な機能、全体像の問い。Phase B へ

迷ったら単純として扱う。

## Phase B: Explore（複雑なときだけ）

問いを 2〜4 の切り口に分ける。切り口は、対象の別々の面（データの流れ、起動から終了までの順序、外部との境界、設定の効き方など）にする。

`subagent-ctl` で explorer を同時に起動する。

1. `spawn(<name>, readonly, --role code)` で読み取り専用のエージェントを、切り口の数だけ起動する。モデルは `code` ロール（`--role` の既定）
2. `send(<id>, <切り口の指示>)` で、担当する切り口と、返す形式（ファイル・行・キーになるシンボル）を渡す
3. `wait(<id>)` の `reason` が `status` になるまで待ち、`read(<id>, <lines>)` で回収する。長い報告はファイルに書かせて読む
4. 回収したら `stop(<id>)` で片付ける

読み取り専用を保証できないハーネスでは、`spawn` が警告を出す。その場合は指示文の冒頭に「読むだけで、ファイルを変更しない」と書き、報告にも 1 行残す。

## Phase C: Synthesize（複雑なときだけ）

explainer を 1 本起動し、explorer の findings をすべて渡して説明を書かせる。モデルは `prose` ロール。説明は Phase D の形式で返させる。

## Phase D: Present

explainer の出力をそのまま出す。会話の文脈を補うための軽い加筆はよいが、大幅な書き直しはしない。

節は次から、当てはまるものだけを使う。当てはまらない節は落とす。

- **概要**: 何をするサブシステムか、どこから呼ばれるか
- **主要な概念**: モデル・用語・状態。初出で短く説明する
- **どう動くか**: 起動から結果までの順序。条件分岐と失敗の道も書く
- **どこにあるか**: ファイルと責務の対応。どのパッケージが何を持つか
- **落とし穴**: 読んだだけでは踏みやすい前提、暗黙の契約、触ると壊れる箇所

## ルール

- 推測で埋めない。読んで分からなかったことは「分からなかった」と書き、何を確かめれば分かるかを添える
- コードは変えない。修正が必要だと分かったら、その旨を報告し、別のタスクとして扱う
- 出力は説明であって、diff ではない。ファイルを列挙するだけの一覧にしない
