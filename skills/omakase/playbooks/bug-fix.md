# Bug fix

**このタスクの責任はあなたにある。計画し、レビューし、検証する。調査と修正は委任するが、主導権は手放さない。**

仮説を立て、実行時証拠で確かめる。コミットする変更の各行は、実行時証拠に辿れる。「役に立つかもしれない」という理由だけで入れる変更は仮説であって修正ではないので、コミットしない。証拠が仮説を否定したら、その仮説を理由に入れた変更を取り消す。証拠から正当化できる最小の変更だけをコミットする。

1. バグが起きるのと同じ実物（画面、CLI、API など）で、**自分で再現する**。再現できないときは、トリガーを合成し、条件を絞り、計測用のコードを入れて、バグが起きる状態を作る。「再現して」と人に頼まない。操作する手段が対象に届かないときだけ、手を尽くした後に理由を具体的に書いて人に頼む。
2. **原因を二分探索する。** 候補仮説を出す前に、`how` で対象がどう動くかを読み、回帰なら `why` で変更の経緯を調べる。候補仮説を実行時証拠で 1 つずつ消す。残ったメカニズムを証拠で確定してから、次の項目へ進む。推測しない。状態が不明なら、計測用のコードやログを足して、実行しながら読む。
3. 修正を計画する。関数の引数や戻り値の形が変わる修正なら、先にデータの形を決める。実装はサブエージェントへ委任する（`subagent-ctl` の 7 動詞を使い、モデルは `code` ロールで指定する）。
4. バグを再現したのと同じ実物で検証する。元の再現手順でバグが出なくなることを確かめる。ユニットテストは分岐の動きを示すだけで、バグが無いことは示さない。判定がつかない場合や、別の実物で検証した場合は合格にせず、その旨を報告する。
5. 失敗する再現手順（テスト）が修正より先に来るように、コミットの順番を決める（`principle-sequence-verifiable-units`）。ローカルで手軽に回せるテストがある場合は、失敗するテストを先にコミットし、そのあと修正をコミットする。テストが高コスト、結合テスト寄り、内容が不明瞭な場合は、この手順を省く。
6. `opening-a-pr` を実行する。

**返信:** 何が壊れていたか、根本原因、修正、どう検証したか。再現手順の出力は、失敗したときと成功したときの両方を貼る。
