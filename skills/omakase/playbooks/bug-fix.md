# Bug fix

**あなたがこのタスクを所有する。計画し、レビューし、検証する。調査と修正は委任し、主導権は持つ。**

科学的に。出荷する各行は実行時証拠に辿れる。「効くかも」の belt-and-suspenders は仮説であって修正ではない。出荷しない。証拠が仮説を否定したら、その動機になった変更を revert する。証拠が正当化する最小の変更だけを出荷する。

1. 対応する実物の surface で**自分で再現する**。再現できないなら、トリガーを合成する、条件を絞る、計装して発火させる。「再現して」と人に頼まない。
2. **原因を二分探索する。** 候補仮説を列挙し、実行時証拠で 1 つずつ消す。残った機構を証拠で確定してから次へ。推測しない。状態が不明なら計装・ログを足して実行しながら読む。
3. 修正を計画する。関数境界を跨ぐなら先に形状を検討する。実装をサブエージェントへ委任する（`subagent-ctl` の 5 動詞。モデルは `code` ロール）。
4. 同じ surface で検証する。元の repro が通る。ユニットテストは分岐挙動を示すのであって、バグの不在を示さない。
5. 失敗する repro が修正より先に来るようコミットを並べる（`principle-sequence-verifiable-units`）。安いローカルテスト経路がある場合は「失敗テスト → 修正」の順で積む。
6. **Opening a PR** を実行する。

**返信:** 何が壊れていたか、根本原因、修正、どう検証したか。失敗→成功の repro 出力を貼る。
