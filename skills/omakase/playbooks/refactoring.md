# Refactoring

**あなたが契約を所有する。構造は変わる。挙動は変わらない。** Feature（挙動を足す）や Bug fix（挙動を直す）と区別する。

掃除の過程で足りない機能や本当のバグを見つけたら、切り離して、ピン留めした契約に対して構造変更を先に出す。大規模・横断的な構造変更は `figure-it-out` へ。このプレイブックは集中的〜中規模の変更。

1. **挙動契約を先にピン留めする。** 対象サブシステムの契約を学び（ソースを自分で読む）、characterization test・snapshot・等価ハーネスで現在の挙動を捕捉してから構造を動かす。カバレッジが無い領域は、構造を動かす前にピンを書く。型チェック・lint はピンではない。
2. **コードに欠けている構造を名付ける。** 分岐の削減、不正状態の排除を目指す。間接参照の追加ではない。
3. **目標形状を名付ける。** 今日作り直すならどうなるか（モジュール構成・型・呼び出しグラフ）。
4. **足す前に引く。** 死んだコード、1 呼び出しラッパー、冗長バリデータ、孤児参照を先に消す。目標形状に達する最小の変更だけを出す（`principle-laziness-protocol`）。「効くかも」の投機的な掃除は revert する。
5. **小さい挙動保存ステップで動かす。** 各ステップでピンを緑に保つ。API 再形成では全呼び出し元を移行して古い API を同じ波で消す。互換 shim を作らない。委任は `subagent-ctl` の 5 動詞（モデルは `code` ロール）。
6. **実物で挙動不変を証明する**（`principle-prove-it-works`）。「コンパイル通った」は証明にならない。
7. **変更が残す価値があるか確認する。** 読者の負荷が下がるか。下がらなければ revert。
8. 小さく順序だったコミットへ rebase する（減算 → 再形成 → 後続の掃除。`principle-sequence-verifiable-units`）。**Opening a PR** を実行する。

**返信:** 変わった構造、ピン留めに使ったもの、等価証明、読者負荷の差分、出荷したものと revert したもの。新しい挙動は無い。
