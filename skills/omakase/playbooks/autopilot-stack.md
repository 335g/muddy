# Autopilot-stack

**ビルドと検証は自動で行い、マージは人が行う。** 独立した PR のキューを、ビルドと検証まで進める。検証済みの PR は merge-ready で止め、マージするかどうかはオペレータに委ねる。

※ このプレイブックは Pi の `fleet_*`（検証ゲート付きのマージ手順）に依存する。他のハーネスへの移植は、必要に応じて後で検討する。

1. **まずオペレータの許可の範囲を確かめる。** オペレータの許可は、キューに入っている項目だけに及ぶ。オペレータが自分の担当だと名指しした項目や、キューに入っていない PR は、merge-ready で止める。
2. **PR ごとにオーナーを 1 人立てる。** オーナーは `fleet_fork`（ワークツリーとセッション）で起動する。起動したオーナーはビルドし、PR を開き、実物で検証し、CI が通るまで落ちた検査を直すことで、merge-ready まで進める。CI と bot が作業と並行して続くようにするため、PR は早めに開く。
3. **オーナーは trunk から並列に走らせ、PR をスタックさせない。** 各 PR は、単独でマージできる。スタックするのは、ある PR が別の PR の上に乗るときだけだ。そのときは、親ブランチを base にする。
4. **検証は作者と別のセッションで行う。** 検証は `fleet_review`（読み取り専用、作者とは別のモデル系統）で行い、結果は `fleet_verdict`（approve か request-changes）で記録する。新しい挙動、再設計、大きな新規の diff は、`swarm` で並列に検証する。rebase、マージ衝突の解消、小さな修正は、新しい head（ブランチの最新コミット）で検証を1回だけ行う。文言だけの変更は検証しなくてよい。判定が有効なのは、1 つの head SHA に対してだけだ。
5. **マージしない。** 各 PR が現在の head で検証済みになり、CI も通ったら、そこで作業を止める。マージするかどうかはオペレータに委ねる。委ねた後は、オペレータの許可がない限り、誰も push しない。
6. **下にある PR の head が変わったら、その上に積んだ PR を積み直す。** 積み直しても `git patch-id` が変わらなかった PR は、前の判定をそのまま使える。

**返信:** マージしたものの代わりに、各 PR を判定付きで列挙する。
