# Autonomous run

**終了条件はあなたが決める。終了条件を満たすまで止まらずに進める。**

1. 作業を始める前に、終了条件を書き出す。たとえば、テストが通る、バグが再現しなくなる、N 本の PR がすべてマージ済み、画像の差分が 0 だ。終了条件は、実行できるコマンド1本（`scripts/predicate.sh` など）として残す。コマンドは合否を exit code で返す。文章で書いただけの終了条件は、1周（変更と検証の1回）ごとに解釈が変わる。何周まで回すか、経過時間の上限も最初に決める。
2. 何をきっかけに再開するかを選ぶ。CI の完走やマージ、ブランチの更新など、待つイベントがあるなら、見張り役のサブエージェントが知らせる。待つイベントが無いなら、一定の間隔で確認する。サブエージェントごとに `wait <id> --timeout <N>` で待ち、戻り値の `reason` で次の対応を決める。`timeout` ならまだ作業中、`status` ならターンが終わった、`exit`・`error`・`blocked` なら脱落だ。複数のサブエージェントをまとめて待つ指定は、hc の端末の中からしか使えない。
3. 1周ごとに、証拠から正当化できる最小の変更を加え、終了条件で検証する。進んだらコミットし、進まなければ捨てる。「役に立つかもしれない」というだけの念のための変更は、残さず戻す。作業は `principle-sequence-verifiable-units` に従って、検証できる小さな単位に分ける。1つの単位を検証してから次へ進む。
4. 作業中に見つけた問題は、自分で処理する。たとえば、壊れたスキル、関係するバグ、結果が安定しない検証、ツールの不具合、放置されたフォローアップ、直せる設計のずれだ。その修正は、別の PR として出す。あとから直せる仕事を人に任せたり、人に聞いたりしない。人に委ねるのは、元に戻せない行動、実験では決まらないプロダクト判断、本当の行き止まりだけにする。常に終了条件を軸にし、個々の修正が終わったら終了条件の確認に戻る。
5. 1周ごとに `show-me-your-work` で記録する。何を変えたか、終了条件が変わったかを1行ずつ残す。
6. 終了条件を満たしたら停止する。数周続けて終了条件に近づかなかったとしても、止まらない。アプローチを変えて、終了条件を満たすまで試し続ける。本当の行き止まりなら人に委ねる。終了条件を緩めて、完了したことにしない。

**返信:** 終了条件、何周回したか、マージされた変更、捨てた変更、最後に終了条件を満たしたか。
