# Figure it out

タスクがどのプレイブックにも合わないとき、1 つ設計する。コードより先に出す成果物はワークフローそのもの。厳密さをタスクに応じてスケールし、科学的方法を回し、人が離れてから監査できる決定の trail を残す。

## Start

最初の項目が「omakase の Principles 節を読む」である todolist を開く。その後、以下のフェーズを todo として足す。

## Phase A: Frame

先に地に足を付けてからコミットする。以下を言えるまで実行を始めない:

- 完了の定義（偽証可能な述語。`principle-prove-it-works`）
- スコープ（定量化: おおよその単位と工数、浮かんだブロッカー）
- 厳密さのレベル（高めに偏る。one-way door とブラスト半径が大きいものほど上げる。厳密さはゲートとアーティファクトであって「頑張る」ではない）

長い実行にコミットする前に、フレーミングとトレードオフを提示する。可逆な作業は進める（`principle-never-block-on-the-human`）。ただし数時間の実行はチェックポイントを 1 つ挟む。

## Phase B: Design the workflow

原子単位（独立して着地可能）に分解する。リスクの高い未知を先に並べる。スキャフォールドと検証を機能より先に作る:

- 作業より先に検証ハーネスを作り、変更前の状態からベースラインを捕捉する（チェックは「旧値 vs 新値」で読めるように）。
- one-way door の設計判断は設計探索を行う。機械的で形状が既に具体的な作業では省略。
- ファンアウトを決める。並列化は seam をまたぐ範囲だけ。各ワーカーに自分のワークツリーかブランチを与える。過剰にファンアウトしない。
- 設計したフェーズ一覧を書く。人がレビューするのはこれ。

設計を実行する。ステップを todo として足し、Phase C のループ規律で各ステップを回し、Phase D のログを織り込む（各ステップが着地するたびに 1 行。最後にまとめてではない）。

## Phase C: Run the loop

各単位は実験。仮説を述べ、最小の変更をし、実物で述語に対して測り、進んだら保持、進まなければ revert。`principle-sequence-verifiable-units` を適用し、各単位を次へ進む前に検証する。

- 検証は artifact を検査する。自己申告では決してない。あまりに簡単に通るなら、システムより先に観測方法を疑う。
- 委任した仕事には判定者を組む。ワーカーがゲートをゲームしたらリセットして契約を固める。ゲート自体が間違っていれば、回り道せずゲートを別の変更で直す。
- 判定は VERIFIED / NOT VERIFIED / INCONCLUSIVE。Inconclusive は合格ではない。否定を隠さない。

## Phase D: Keep the audit trail

`show-me-your-work` で実行を記録する。figure-it-out の仕事は通常、レビュー担当者が PR 内で読めるよう trail をコミットする価値がある。trail + diff が、人が戻ってきて仕事を信じられる理由になる。

## Phase E: Verify and hand back

Phase A の述語に対して、ハーネスだけでなく実物で全体を検証する。繰り返す訂正はゲート・lint・チェック・スクリプトに落とす。

**返信:** 設計したプレイブック、厳密さのレベルと理由、決定 trail のパス、述語に対して検証されたもの、未解決の点。
